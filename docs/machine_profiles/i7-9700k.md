# Benchmark baseline: i7-9700K (`jebel`)

The benchmark machine's baseline: every timing a later number can be checked against, all from
one tagged commit pair. This is the companion of the machine's profile,
[i7-9700k.json](i7-9700k.json), which `scripts/ab.py`'s machine check compares against
(`PROFILE_REFERENCE`). When the baseline is re-recorded, this file is replaced in place, with the
reason in the PR; git has the history. The noise rules that use these numbers are in
[measurement.md](../measurement.md).

Planned and recorded by the benchmark machine workplan (D6-D8), now retired:
`git show 480164d:docs/benchmark-machine-workplan.md`.

## The machine

| | |
| --- | --- |
| CPU | Core i7-9700K: 8 cores, 8 threads (no SMT), 800-4900 MHz (base 3600) |
| caches | L1d 32 KB and L2 256 KB per core, L3 12 MB shared |
| ISA | AVX2, FMA; no AVX-512 |
| memory | 31 GB, 8 GB swap |
| OS | Ubuntu 26.04.1, kernel 7.0.0-38-generic |
| Python, numpy | CPython 3.14.4, numpy 2.5.3 with scipy-openblas 0.3.34 (`DYNAMIC_ARCH`, Haswell kernels) |
| Rust | rustc 1.98.1 |

The profile holds the full identity. A field that changes (a kernel, numpy or rustc update, a
reset power limit) makes the machine check refuse a run, and may move every number here (After
the workplan: rerunning the baseline).

**Frequency policy (D1): the defaults.** `intel_pstate` active (HWP), governor `powersave`, EPP
`balance_performance`, turbo on. Stage 2 chose it over EPP `performance` for its smaller
pass-to-pass spread (median 3.2% against 3.5%, max 5.6% against 7.2%). A core clocks up from idle
in about 3 ms.

**Package power limit (D10): PL1 65 W,** PL2 120 W. At the stock 95 W a ten-minute all-core load
reached 100 C and throttled; at 65 W it holds about 3.7 GHz and 78 C. Single-core work (about
37 W) and the threaded conv case (about 40 W) never reach the limit.

**Setup after every boot:** `sudo scripts/benchmark_machine_setup.sh` sets the policy, the power
limit and `perf_event_paranoid` 2, and holds snap refreshes. It prints `PL1, PL2: 65 W, 120 W`
when the limit is applied. All of these reset on reboot, and the machine check refuses a run until
the script has been re-run.

## Rerunning it

Before any run: the setup script since the last boot (it stops `thermald`, which would put PL1
back to 95 W), then measurement.md §2's checks (`uptime`,
`ps`, no browser, `systemctl is-active apt-daily.service apt-daily-upgrade.service` printing
`inactive` twice). One run at a time, in the background.

**The crate under test is the venv's.** When both sides have the same crate commit, as at the
tag, `ab.py` uses the venv's extension, and that is built from this checkout's `rust/`. So
`rust/` has to be at `66ecc0d` and built first:

```sh
git -C rust checkout baseline-i7-9700k && ./cli build-rust
```

**Stage 4, the A/As:** one run per adapter, at its default arguments:

```sh
for bench in prepared_dataset_timing focused_benchmark epoch_op_profile \
             accuracy_pass_timing op_call_timing batch_size_timing; do
    .venv/bin/python scripts/ab.py run --bench $bench \
        --old baseline-i7-9700k --new baseline-i7-9700k --name baseline-aa-$bench
done
```

(Run one at a time, as listed, with the checks before each; the loop shows the arguments.) Each
run's table here is `ab.py report <run> --pooled FILE`, and its noise row comes from the same
file.

**Stage 5, outside `ab.py`,** one process per measurement (measurement.md §6), from a worktree at
the tag:

- per-op table: `scripts/focused_benchmark.py --shape 5408 --shape 784 --op forward_batch
  --op downstream_batch --op accumulate_gradient_batch`, then again with `--rust-threads 1
  --openblas-threads 1`;
- conv demo ratio table:
  `python -m indrajala_ml.demos.conv.demo_conv_rust_vs_vectorized_digit_recognition`;
- kernel protocol configurations: the conv epochs by `prepared_dataset_timing.py --configs "conv
  B=32" "conv B=512"` (the B=512 config is new in stage 5), the dense ones from the
  `batch_size_timing` A/A;
- where a Rust epoch spends its time: the `epoch_op_profile` A/A's conv rows.

Stage 4's A/As already cover the default-threading per-op table, the dense kernel configurations
and the op profile, so stage 5 adds only what they don't. Each table below names its run.

## Noise

From the six A/As below: `baseline-i7-9700k` against itself, `ONNONO`, 2026-10-08, run one at a
time with the setup script applied and `thermald` stopped. PL1, logged once a minute, stayed at
65 W throughout. The pre-flight 1-minute load was 0.15-0.96, the latter being what the previous
run left behind. No process went above 10% of a CPU, except Claude Code once in the first run.

| --- | --- | --- | --- | --- |
| `prepared_dataset_timing` | 24 | 2.2% / 5.6% / 7.7% | 0.6% | none |
| `focused_benchmark` | 258 | 2.8% / 5.9% / 53.7% | 0.5% | 6, each 1.1-1.7% |

The spread is a row's range of per-pass medians over all six passes, as a % of its pooled median.
A pass's shift is the median over rows of its median against the pooled one (`ab.py report
--pooled` computes both). None of the 36 passes came near the 5% shifted-pass threshold.

**The rules these numbers set** are this machine's `noise_rules` in its profile (#582):
`shifted_pass` 2%, still twice the largest shift seen; `high_load` 1.5, kept, since the pre-flight
load never passed 0.96; and `small_consistent` 2%, under which a *consistent* row is marked small.
The verdict rule is unchanged. These six runs ran before the rules existed, so their own reports
(below) use the defaults: 5%, 1.5, and no small mark.

- **The flagged rows are chance.** Seven of 591 rows were flagged *consistent*, every one under
  2%. In all of them but two, single processes overlap between the sides. The two exceptions are
  under 3% (numpy `conv 26x26x8/2 forward` and `dense 10 x 30 add b512`). The sides alternate in
  time, so this isn't drift. Read a *consistent* row under about 2% from one A/B with care.
- **Single-process spikes.** One process can run far off its pass's median while the others agree:
  numpy `conv tail 32 x 5408 transpose b512` ran 18.4 µs in one pass, against 11.8-12.7 in the
  other five. Most of the large maxima are this, or microsecond ops in `epoch_op_profile` (the
  `layer_output_delta` and `default_rng` rows), where any jitter is a large share.
- **Per-process modes in one Rust op.** The single-example Rust `downstream` on the 32 x 5408 conv
  tail settles, per process, at about 20.8, 22.1-22.4 or 23.8 µs, each process steady within 2%.
  It did so in both of the day's `focused_benchmark` A/As. In this morning's, the old side drew
  the low level more often, and the row read +12.9% *consistent*. A difference of up to about 15%
  in this row can come from the modes alone. Stage 6 traced the slow modes to L2 misses (Laptop
  findings, re-checked: Per-process modes).

### Per-process modes

`focused_benchmark.py --shape pool --shape "conv tail" --op downstream --batch-sizes 32 --passes
20`, both backends (`stage6-process-modes`): 20 processes per case.

- **The max-pool downstream at batch 32 has no modes here:** Rust 157.6-161.6 µs (2.5%), numpy
  475-510 µs with a continuous tail. The 6x6 pool is as tight.
- **The conv tail's single-example Rust `downstream` does** (stage 4 saw it in both A/As): 11
  processes at 20.5-21.1 µs, 3 at 21.9-22.3, 6 at 23.2-23.8, each steady. `perf_region.py` over
  16-20 processes of 20000 calls each (`driver_conv_tail_downstream.py` and `perf*.txt` in the run
  directory):

  | per call | fast (about 21 µs) | slow (about 24 µs) |
  | --- | --- | --- |
  | cycles | 99-100k | 112-114k |
  | instructions | 105.4k | 105.4k |
  | `l1d.replacement` | 23.2k | 23.2k |
  | `cycle_activity.stalls_l1d_miss` | 26.6k | 37.7k |
  | `cycle_activity.stalls_l2_miss` | 16.4k | 31k |
  | `mem_load_retired.l2_hit` / `l3_hit` | 6600 / 714 | 6100 / 1085 |

  4K aliasing, store-forward blocks, the store buffer and the DSB/MITE split don't move. The slow
  processes send about 50% more demand loads past L2: the same misses, served from further away.
  Physical page placement in L2's sets is the likely cause (not tested). A different mechanism
  from the laptop's mode (scheduler stalls, same cache traffic), and nothing in the crate to tune;
  a difference of up to about 15% in this row can come from the modes alone.
